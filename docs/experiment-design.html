01

SXM과 HBM은 다른 분류

SXM은 GPU 모듈의 장착 형태다. High Bandwidth Memory(HBM)는 GPU에 연결된 고대역폭 메모리다. 실험 대상은 V100·A100·H100 SXM이며 HBM은 측정할 계층이다.

02

기준을 세 가지로 보고한다

전체 에너지, 같은 조건의 전후 idle 대비 증가분, 짝지은 active reference 대비 차이를 분리한다. 기준 차감값을 순수 회로의 dynamic 에너지로 해석하지 않는다.

03

최적 주파수는 결과가 결정한다

지원 범위에서 약 90 MHz 간격으로 탐색하고, 각 GPU UUID별 검증된 측정점을 비교한다. 세 GPU에 같은 최적 MHz나 pJ 단가를 미리 부여하지 않는다.

01 / SCOPE & UNITS

장치, 센서 범위, 분모를 먼저 고정한다

대상은 모두 SXM 모듈이다. 대표 표기는 V100 SXM2·A100 SXM4·H100 SXM5이며 실제 SKU를 discovery로 확인한다. L1/L2는 Level 1/Level 2 cache다. 같은 이름 안에서도 메모리 용량·SKU·power limit이 다를 수 있으므로 이름만으로 사양을 넣지 않는다. discover에서 실제 GPU UUID, SM 수, 메모리·L2 용량, 지원 클럭, 센서 범위를 기록하고 해당 장치 정보로 계획을 만든다.

02 / WORKLOAD & GEOMETRY

어떤 자원을 얼마나 쓰는지 함께 sweep한다

Streaming Multiprocessor(SM)는 thread를 실행하는 계산 단위이고, warp는 32개 thread 묶음이다. block은 함께 실행·협력하는 thread 묶음이며 실제 SM 배치는 scheduler가 정한다. Graphics Processing Cluster(GPC)는 여러 SM을 묶는 계층이다. blocks = SM 수 × 계수는 동시 작업량을 조절하는 설정이며 물리 SM을 켜고 끄는 명령이 아니다.

03 / TREATMENT & REFERENCE

Idle 한 숫자를 단순히 빼는 설계로는 부족하다

Treatment는 측정하려는 Tensor·L1·L2·HBM 작업이다. Reference는 같은 장치·클럭 정책·컨텍스트·할당에서 비교하는 기준이다. idle 기준은 커널이 쉬는 상태이고, active reference는 실제로 실행되는 제어 커널이다. 둘은 다른 질문에 답한다.

전체 에너지: 실제 업무의 총 비용

e_total = E_treatment / N_treatment

측정 구간의 전체 GPU 에너지를 그 구간에서 완료한 작업 수로 나눈다. idle·refresh·제어·연산·데이터 이동이 모두 포함된 관측값이다. 기준 상태 차이에 따른 차감 편향이 없는 주된 효율 지표다.

해석: GPU 전체 업무 단가. 특정 Tensor/L1/L2/HBM 회로만의 에너지는 아니다.

전후 idle: 운영상 기준

전후 idle를 active 시각에 보간해 drift를 반영한다. 요청 클럭이 같아도 idle clock gating으로 실제 MHz가 내려갈 수 있다. active와 idle의 실제 클럭·온도·간섭 조건이 맞는지 별도 판정한다.

일치하지 않으면 관측된 증가분을 보존하되, 기준 차감 효율 최적값의 후보로 승인하지 않는다.

Active reference: 짝지은 대비

grid·thread·iteration·SM filter·batch 설정과 context/allocation을 공유하는 issue-loop control을 짝짓는다. 각 arm을 warmup하고 AB/BA로 순서를 균형 배치해 순서·온도 영향을 살핀다. 조회 가능한 pstate와 enforced power cap의 일치도 확인한다.

control도 integer ALU·제어·launch·store 전력을 쓴다. 대상과 register/occupancy·명령·cache 상태가 완전히 같다는 가정은 하지 않는다. 기본 paired 대상은 custom Tensor·L1·L2·HBM이며, cuBLAS GEMM에 완전히 대응하는 reference는 제공하지 않는다.

정확한 해석: idle 증가분에는 activation·실제 주파수 상태·누설 변화가 섞일 수 있다. active-reference 차이에는 두 프로그램의 명령·cache·occupancy 차이가 섞인다. 어떤 기준도 단독으로 순수 static/dynamic 또는 순수 Tensor/L1/L2/HBM 회로 에너지를 분리하지 않는다. 전체 단가와 각 operational contrast를 함께 보고하고, 승인된 기준에 대해서만 별도 최적점을 선택한다.

왜 반복·온도·순서가 중요한가?

앞 arm이 GPU를 데우면 뒤 arm의 누설·boost 상태가 달라질 수 있다. 한 번의 A→B 차이는 이 영향을 treatment 효과로 오인할 수 있다. AB/BA 균형 반복(기본 4회), arm별 actual clock·온도·throttling 검사, 전후 drift, 시간 정렬, paired contrast의 반복 불확실성으로 문제를 드러낸다. 보정되지 않는 차이는 인과 효과로 단정하지 않는다.

04 / SUPPORTED CLOCK GRID

약 90 MHz sweep + default + 정확한 1110 MHz

기존 구현의 quantile 선택은 약 90 MHz 격자를 보장하지 않았다. 이제 주파수 탐색 계획은 장치가 광고한 지원 clock pair에서 약 90 MHz 간격의 목표점을 매핑하고, 가능한 범위의 끝점과 필수점을 포함한다. 지원 목록이 이산적이므로 실제 간격은 90 MHz와 조금 다를 수 있고, 모든 매핑·간격을 plan에 남긴다.

포함할 조건계획에서의 처리오해를 피할 기록
~90 MHz 격자선택한 memory clock마다 지원 graphics clock 목록에서 목표 grid를 매핑한다.요청 grid, 실제 선택 MHz, 매핑 오차, 실제 인접 간격
1110 MHz그 memory domain에서 정확히 지원될 때 반드시 포함한다.미지원 exact pair는 적용 불가(not-applicable) 사유를 남김. 1100/1125 등의 근사값을 1110으로 표시하지 않음.
현재 default-policy reference클럭을 새로 요청하지 않는 null/null 조건을 포함한다.실행 전 들어온 정책과 실제 동작 MHz를 보존. 이전 사용자 설정이 있다면 factory default와 다름.
광고된 default 고정 pair장치가 광고한 기본 graphics/memory pair가 지원되면 별도 고정 조건으로 포함한다.기본 pair와 지원 여부. grid와 같으면 condition을 중복 실행하지 않고 사유를 합침.

90 MHz는 core/graphics 도메인의 탐색 간격이다. HBM memory clock은 별도의 지원 목록에서 선택한다. saturation·DVFS·locality 설정 모두 모든 광고된 memory domain을 약 90 MHz graphics 간격으로 따로 탐색한다. 같은 raw memory MHz가 세 HBM 세대에서 같은 bandwidth를 뜻하지 않는다. Dynamic Voltage and Frequency Scaling(DVFS)의 전압·gating·power cap 영향은 요청 MHz만으로 제거되지 않으므로 실제 MHz와 상태를 함께 검사한다.

단계적 실험: 여러 resource geometry를 포함한 약 90 MHz coarse sweep → 실측 최소점 주변의 지원 15–30 MHz 이웃 등 추가 refinement. refinement는 실제 지원 목록 안에서 새 조건·새 반복을 생성해야 하며 곡선 보간으로 측정값을 만들지 않는다.

브라우저에서만 읽는다. 서버 전송·외부 네트워크 요청은 없다.

아직 plan을 불러오지 않았다. 아래에 지원 주파수나 coverage를 임의로 채우지 않는다.

05 / VALIDITY BEFORE EFFICIENCY

NCU 통과, 높은 처리량, 에너지 최소는 서로 다른 판단이다

NVIDIA Nsight Compute(NCU)로 목표 작업이 실제 Tensor·L1·L2·HBM 경로를 사용하는지 확인한다. counter 측정은 replay와 overhead가 있으므로 전력 측정과 분리한다. 같은 UUID·binary hash·effective parameter·actual clock에 대한 evidence를 연결하고 분석 때 다시 평가한다. paired allocation은 유지하지만 NCU profile 구간에는 reference arm을 넣지 않는다.

기본 counter 정책과 제한

L1/L2 read hit ≥95%, cache의 하위 traffic ≤logical byte의 10%, L2/HBM read의 L1 hit ≤5%를 시작 정책으로 사용한다. HBM read는 L2 hit ≤20%, 요청 방향 DRAM/logical byte ≥0.75, DRAM/L2 byte 비율 0.75–1.25를 확인한다. sector inflation 범위는 0.90–8.25, actual clock 오차·drift는 3%다. 정책값은 실험 판단 규칙이며 물리적 상수는 아니다. L2 write/copy는 read-hit만으로 residency를 증명하지 못해 미확정으로 남긴다.

실제 GPU가 없는 개발 환경의 unit test·CUDA 빌드는 sensor·cache 적절성의 실장비 검증이 아니다. V100의 NCU 검증은 GV100 지원 버전(예: 2025.2.x)이 필요하다. 전력 API의 평균 창과 NCU metric 지원은 장치에서 확인한다.

06 / EMPIRICAL OPTIMUM

최적값은 각 GPU의 결과에서 독립적으로 뽑는다

세 GPU에 공통 최적 MHz를 가정하지 않는다. 동일 GPU UUID·workload·access·memory clock·power/환경 층에서 core clock과 geometry를 비교한다. 각각의 관측점에 높은 활용 조건과 검증 evidence를 적용한 뒤, objective별 최소 단가를 선택한다.

  1. 측정점 품질을 승인한다. 반복 수·센서·간섭·actual clock·온도·시간 정렬과 NCU를 확인한다. baseline/reference는 가능한 pstate·enforced power cap도 비교한다. 미검증 기록도 원본에 남지만 verified 최적점의 후보가 되지 않는다.

  2. 각 주파수에서 충분히 활용한 geometry를 찾는다. 그 frequency pair에서 최소 2개의 서로 다른 resource geometry를 실제로 비교해야 한다. 비교한 유효 geometry 중 관측 최고 처리량을 분모로 하고 기본 95% 이상을 요구한다. 검증된 후보만으로 peak를 낮추지 않는다. 검증된 geometry가 하나뿐이면 자기 자신 대비 100%일 뿐이므로 승인된 효율 최적점 대신 탐색 진단으로 남긴다.

  3. 각 objective의 최소를 선택한다. 전체 pJ/bit·pJ/FLOP, 승인된 idle 증가분, 승인된 paired-reference 대비를 별도로 비교한다. reference 상태가 미승인인 차감값은 winner가 없으며 paired 최적점에는 AB와 BA의 유효 반복 수가 같아야 한다. 기본 설정은 4회이며 odd/탈락 반복에 의한 불균형은 진단에 남긴다.

  4. 주변 측정점과 불확실성을 함께 남긴다. near-optimal support points와 불확실성이 겹치는 support points를 표시한다. 두 측정점 사이의 모든 주파수가 최적이라는 연속 구간 주장은 하지 않는다.

  5. 최고 처리량 요구조건은 별도로 보고한다. 전체 clock sweep 최고 처리량의 95% 이상을 요구하는 cross-clock 선택도 유지한다. 주파수별 활용 효율 최적점과 최고 성능 근처 최적점은 서로 다른 운영 목적이다.

주파수별 활용 효율 최소

각 MHz에서 2개 이상의 resource geometry를 비교하고 관측 peak 근처 조건의 에너지 단가를 비교한다. 최소 비교 수가 실제 하드웨어 plateau의 증명은 아니다. 낮은 MHz에서도 주어진 도메인을 충분히 사용했다면 후보가 될 수 있다.

사용 목적: workload의 효율 좋은 동작점·주파수 구간 조사.

전체 최고 성능 근처 최소

모든 clock 조건 중 관측 최고 처리량의 95% 이상인 결과만 비교한다. 에너지 단가가 낮아도 처리량 제약을 못 맞추면 제외한다.

사용 목적: 성능을 크게 낮추지 않는 실제 운영 설정.

Winner는 측정한 지원점 중 최선이다. 측정하지 않은 영역·다른 온도·다른 power cap·다른 GPU UUID까지 보장하지 않는다. 90 MHz coarse 최소점 주변을 추가 측정해 resolution을 높일 수 있다. 세 GPU의 최적 구간이 겹칠 수도, 다를 수도 있으며 어느 쪽도 미리 정하지 않는다.

07 / LOCAL RESULTS VIEWER

실제 summary.json으로 GPU별 최적점을 확인한다

분석 프로그램이 만든 summary.json을 불러오면 GPU·workload·access·memory clock·objective별 최적점과 주변 실측 support point를 표시한다. 단일 resource geometry 결과는 승인된 최적점과 별도 진단으로 표시한다. 빈 화면에 예시 수치를 넣지 않는다. 이 뷰어는 summary의 판정 결과를 보여주며 원시 evidence를 새로 검증하지 않는다. fixed-memory 최적점과 모든 measured memory domain을 함께 비교한 최적점을 분리해서 표시한다.

업로드라는 표현 대신 로컬 읽기: 파일 내용은 이 브라우저 안에서만 처리된다.

아직 결과를 불러오지 않았다. GPU별 최적 pJ/bit·pJ/FLOP는 미측정 상태다.

실측 결과 없음 · V100/A100/H100의 최적 주파수·전력·idle 비율을 아직 숫자로 확정할 수 없다.
Physical pJ/bit와 logical pJ/bit를 함께 읽는 방법

stride가 커지면 같은 logical bytes를 처리하면서 더 많은 sectors가 움직일 수 있다. 그러면 logical 단가와 physical 단가가 서로 다른 방향으로 변할 수 있다. 별도 NCU의 byte count는 목표 path를 검증하는 근거다. 지속 전력 구간의 실제 물리 전송량과 시간 기준이 증명되지 않으면 그 count를 그대로 전체 E의 분모로 붙여 physical pJ/bit를 만들지 않는다. 해당 provenance가 없으면 physical 단가는 미확정으로 남긴다.

08 / EXECUTION & INTERPRETATION

계획 → 전력 측정 → NCU → 분석

실행 전 GPU가 독점적이고 현재 정책을 복원할 수 있는지 확인한다. energy-sweep 계획의 execution_allowed가 false이면 요구사항 coverage를 먼저 보완하며 runner는 clock 변경과 kernel 실행 전에 차단한다. 기록된 native 지원 목록에서 필수 약 90 MHz grid를 다시 계산하고 각 geometry·treatment design 층의 실제 clock trial coverage를 검사한다. 무설정 smoke는 진단 목적의 예외이고 full sweep 승인으로 표시하지 않는다. 각 단계의 UUID·binary·clock 조건을 같은 provenance로 연결한다. 실제 실행·센서 준비 시간을 제외한 plan의 최소 예상 시간은 참고치이며 sweep가 커지면 수시간이 걸릴 수 있다.

python -m powermodeling discover --device 0 --bench build/powerbench
python -m powermodeling plan --config configs/dvfs.json --device 0 \
  --bench build/powerbench --output dvfs-plan.json
python -m powermodeling run --plan dvfs-plan.json --device 0 \
  --bench build/powerbench --output results/dvfs \
  --apply-clocks --clock-method applications
python -m powermodeling validate-run --plan dvfs-plan.json \
  --input results/dvfs --output results/dvfs-validated \
  --profiles-dir profiles/dvfs --device 0 --bench build/powerbench \
  --apply-clocks --clock-method applications
python -m powermodeling analyze --input results/dvfs-validated \
  --output results/dvfs-report

400 W·312 TFLOPS 등의 정격값에서 idle를 역산하지 않는다. 실제 idle W, 부하 W, power limit, actual MHz와 workload 단가를 별도로 보고한다. FP16 dense 성능과 sparsity를 사용한 표기, 사양상 peak와 실측 지속 처리량도 섞지 않는다.
