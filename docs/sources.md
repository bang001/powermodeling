# Primary sources and experimental decisions

Reviewed 2026-10-05 (UTC). These links support architectural facts and API semantics. Measurement durations, 95% throughput threshold, grid sizes and analysis rejection tolerances are project policies, not NVIDIA guarantees. No hardware energy result is claimed by this document.

| ID | Primary source | Relevant section and consequence |
|---|---|---|
| S1 | [NVML Device Queries](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlDeviceQueries.html) | `nvmlDeviceGetPowerUsage`: power includes GPU and associated circuitry, such as memory; GA100 and older return instantaneous power, Ampere except GA100 and newer return power averaged over one second. `nvmlDeviceGetTotalEnergyConsumption`: millijoules since driver reload, Volta or newer fully supported devices; unsupported/error states must be recorded. |
| S2 | [NVML Field Value Enums](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlFieldValueEnums.html), [NVML Device Enums](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlDeviceEnums.html), [Field Value Queries](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlFieldValueQueries.html) | `NVML_FI_DEV_POWER_AVERAGE`, `NVML_FI_DEV_POWER_INSTANT`, `NVML_POWER_SCOPE_GPU`, `NVML_POWER_SCOPE_MODULE`, `NVML_POWER_SCOPE_MEMORY`, `nvmlDeviceGetFieldValues`. A constant exposed by a binding is not proof that a device supports it. Store per-field status, scope and timestamps; use exported constants rather than guessed numeric IDs. |
| S3 | [NVIDIA A100 Tensor Core GPU Architecture whitepaper](https://www.nvidia.com/content/dam/en-zz/Solutions/Data-Center/nvidia-ampere-architecture-whitepaper.pdf) | Printed pp. 34–36, “A100 L2 Cache” and comparison table: two L2 partitions, each 40 slices of 512 KB; GPC-local access with hardware coherence, compute data compression, 40 MB-class total L2. Figures describe physical organization, not an API assigning CUDA virtual addresses or individual SM IDs to partitions. |
| S4 | [Volta Tuning Guide](https://docs.nvidia.com/cuda/volta-tuning-guide/index.html) | “Unified Shared Memory/L1/Texture Cache”: shared 128 KB capacity, selectable carveout, residency/occupancy tradeoffs. “High Bandwidth Memory”: concurrent memory accesses are needed to hide latency. |
| S5 | [Ampere Tuning Guide](https://docs.nvidia.com/cuda/ampere-tuning-guide/index.html) | A100 compute capability 8.0 has a 192 KB combined shared/L1/texture resource; shared-memory carveout and L2 residency affect effective capacity. Do not generalize GA10x behavior to A100/GA100. |
| S6 | [Hopper Tuning Guide](https://docs.nvidia.com/cuda/hopper-tuning-guide/index.html) | H100 combined shared/L1/texture capacity is 256 KB; nominal L2 grows to 50 MB. | S7 | [NVIDIA Hopper Architecture In-Depth](https://developer.nvidia.com/blog/nvidia-hopper-architecture-in-depth/) | “H100 L2 cache”: 50 MB, partitioned crossbar, local GPC access. “Compute Capability” and block-cluster sections: 32-thread warps and hierarchy. The launch article explicitly labels its H100 performance tables **preliminary**; shipped SKU performance comes from S12, not these tables. It does not publish a general CUDA SM-ID/address-to-partition mapping. |
| S8 | [PTX Instruction Set Architecture](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html) | “Cache Operators”: `.ca` caches at all levels, `.cg` caches at the global level. These are performance hints and do not guarantee placement. `.cg` is suitable for bypassing L1, not for isolating HBM while bypassing L2. “Special Registers”: `%smid` reports the current SM identifier; it does not document GPC or L2-partition mapping. |
| S9 | [Nsight Compute Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html) | “Replay”, “Clock Control”, “Cache Control”, “Memory Tables”: profiling can replay kernels, flush caches and alter clocks. Collect counters separately from energy. Sector is 32 bytes; cache line is 128 bytes. L2 Fabric Total describes traffic crossing the fabric between partitions where supported. Query available metrics rather than assuming a stable cross-generation name. |
| S10 | [nvidia-smi documentation](https://docs.nvidia.com/deploy/nvidia-smi/index.html) | Clock locks/application clocks, power limits and clock event reasons have device/permission constraints. GPU utilization is time with one or more kernels executing; memory utilization is time with memory accesses, not achieved byte bandwidth. “GPU Memory Power Readings” defines average last-second and instantaneous readings; the changelog adds reporting between v535 Update and v545 without promising support on all H100s. |
| S11 | [NVIDIA A100 80GB datasheet, Jan 2021](https://www.nvidia.com/content/dam/en-zz/Solutions/Data-Center/a100/pdf/a100-80gb-datasheet-update-nvidia-us-1521051-r2-web.pdf) | p. 1: SXM 40 GB and 80 GB maximum TDP 400 W; dense FP16 Tensor 312 TFLOPS, structured-sparse 624 TFLOPS; HBM bandwidth 1,555 and 2,039 GB/s. These are specification limits, not measured simultaneous power/performance pairs. |
| S12 | [NVIDIA H100 current product specifications](https://www.nvidia.com/en-sg/data-center/h100/) | Current shipped SXM and NVL specifications distinguish GPU memory, bandwidth and TDP. SXM FP16 1,979 TFLOPS is starred **with sparsity**; dense comparison is approximately half, subject to rounding. SXM power is configurable up to 700 W and bandwidth is 3.35 TB/s. The NVL column is a different SKU. |

| S14 | [CUDA Toolkit 13.0 release notes](https://docs.nvidia.com/cuda/archive/13.0.0/cuda-toolkit-release-notes/index.html) | “Deprecated Architectures”: offline compilation and library support for Volta were removed in CUDA 13.0. Use CUDA 12.x to build a comparison binary with `sm_70`, `sm_80` and `sm_90`; an H100-only CUDA 13 build cannot be used as the same V100 binary. |
| S15 | [cuBLAS documentation](https://docs.nvidia.com/cuda/cublas/index.html), [CUDA C++ Programming Guide 12.9.1](https://docs.nvidia.com/cuda/archive/12.9.1/cuda-c-programming-guide/index.html) | GEMM datatype/computation mode and warp-level matrix operations must be explicit. | S16 | [Nsight Compute CLI](https://docs.nvidia.com/nsight-compute/NsightComputeCli/index.html) | `--profile-from-start off` enables application-controlled profiler start/stop; `--devices` selects CUDA device indices for profiling and metric queries. `--log-file` separates tool output, `--csv --page raw --print-units base` preserves machine-readable base units. ## Claims that require measurements

- The minimum pJ/FLOP or pJ/logical-bit of a specific SXM GPU and its idle power.
- Whether a working set is actually served predominantly by L1, L2 or HBM.
- Which SM/address combinations are near/far on a given board.
- Whether a memory-power scope is available and what circuitry its sensor includes.
- The lowest SM/memory frequency pair that retains the observed maximum bandwidth.
- The additive validity of coefficients when Tensor and memory paths operate concurrently.

The code records observables and analysis assumptions. Whole-device total energy, matched powered-idle increments and paired active-reference contrasts are separate objectives. Baseline contrasts and workload slopes remain operational estimates unless independently validated with counters/rails and suitable mixed-workload holdouts.
